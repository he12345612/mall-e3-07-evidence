# E3-07 无效地址更新清空已有默认地址

## 选题与既有契约

- Issue：[E3-07 Issue #13](https://github.com/meng004/mall/issues/13)。
- 基线：`baseline-dcaa93b3`。
- 调用链：`UmsMemberReceiveAddressController.update`（`/member/address/update/{id}`）→ `UmsMemberReceiveAddressServiceImpl.update`（`mall-portal/src/main/java/com/macro/mall/portal/service/impl/UmsMemberReceiveAddressServiceImpl.java:41`）→ `UmsMemberService.getCurrentMember()` → `UmsMemberReceiveAddressMapper`。
- 用户故事：作为会员，我只能更新自己的收货地址；若目标不存在或属于他人，系统应返回 0，不得改变我的默认地址。
- 验收准则：无效目标不产生写入；有效非默认地址设为默认时先清原默认再更新目标并返回 1；已是默认、普通字段更新、`defaultStatus=null` 视为 0，且继续使用当前会员过滤。
- 不得修改：表结构、接口签名、`UmsMemberReceiveAddressService#update` 上的 `@Transactional`；不扩展并发唯一默认、添加和删除地址规则。

## 第一个失败测试与改前红灯

第一个业务测试是 `missingDefaultTargetDoesNotWrite`：当前会员为 101，目标地址 999 不存在，请求 `defaultStatus=1`，期望返回 0，并断言 `addressMapper.updateByExampleSelective` 从未调用。

它在修改前必须失败，因为原服务只按“当前会员 + 地址 ID”构造更新条件，却在尚未确认目标是否存在时就先执行“清除当前会员默认地址”；随后目标更新为 0 行，原默认已经被清空。

改前实测：`Tests run: 6, Failures: 2, Errors: 0, Skipped: 0`。两个失败分别是不存在地址和他人地址；Mockito 均报告发生两次更新调用：先传 `defaultStatus=0` 的记录清默认，再更新目标。完整日志见 `evidence/baseline-test.log`。

## 最小修改与依据

在 `UmsMemberReceiveAddressServiceImpl.java:46` 增加：

```java
if (addressMapper.countByExample(example)==0){
    return 0;
}
```

依据是：`example` 已同时包含当前会员 ID 和目标地址 ID，因此计数为 0 准确表示该目标不可更新。该检查发生在任何写入之前，保留原有会员过滤、默认状态归一化、写顺序和事务声明。没有改表结构、接口签名，也没有增加并发唯一默认规则。

这里拒绝“先更新目标，再清默认”的方案：后一次清默认条件仍是“当前会员且默认=1”，会把刚设为默认的目标再次清成 0，破坏成功语义。

## 断言未放宽与验证

原来用于锁定缺陷的“无效目标不写入”断言保持不变：`verify(addressMapper, never()).updateByExampleSelective(any(), any())`。没有删除断言，也没有改成更宽松的结果判断。

有效地址设为默认时，测试捕获两次写入并确认顺序为：先把当前会员原默认改为 0，再更新目标为默认；目标更新条件仍包含当前会员 101 和地址 321。普通字段更新及 `defaultStatus=null/0` 只发生一次目标更新。

改后同组实测：`Tests run: 6, Failures: 0, Errors: 0, Skipped: 0`。见 `evidence/fixed-test.log`。

## 调用、持久化与证据范围

数据流为：HTTP 地址 ID 与请求体 → 当前会员 ID → 查询“当前会员 + 目标 ID”是否可更新 → 有效且请求设为默认时清原默认 → 按同一会员与地址条件更新目标。接口层已有 `@Transactional`，本次保留；正常返回 0 不会触发异常回滚，所以不能靠事务声明掩盖先写默认再更新 0 行的问题。

未验证：隔离 MySQL 上的真实提交/回滚、完整 HTTP 认证链、并发删除与并发设置默认。本次测试为真实服务加 Mapper 替身，不把 Mock 绿灯表述为数据库端到端证据。
